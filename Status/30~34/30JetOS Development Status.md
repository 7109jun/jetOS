## Philosophy

> **"An OS for people who want to use Windows but cannot afford it."**

Milestone 30 changes direction once again: **"Build a C compiler/runtime for JetOS itself."**

The project's existing principle — implementing bignum/RSA/SHA-256/AES completely from scratch without depending on external cryptographic libraries — is applied to the compiler backend as well:

**JCC generates x86-64 machine-code bytes directly, without using an external assembler (`as`) or linker (`ld`).**

JCC is implemented as a host-side tool, similar to `mkjetfs.c` and `jetfs_import.c`, while its output uses a format that `kernel/exec/elf_loader.c` already understands: a static ELF64 executable running as a Ring3 isolated process. No separate loader work was required because the existing M15 ELF execution infrastructure could be reused.

The verification methodology has also advanced another step.

Previously, verification primarily consisted of compiling kernel code on the host and testing individual functions. This time, **the actual machine-code bytes generated by JCC were executed by a real x86-64 CPU**.

A host harness uses `mmap` to map the generated program at its exact link address, replaces the `_write`/`_exit`/`_gettick` syscall trampoline locations with real host functions, and invokes the entry point through a function pointer.

This is **not an emulator**. The generated machine code is executed directly by the sandbox's actual CPU.

## Build & Run

```bash
make jcc
# Build the host-side C compiler -> build/jcc

./build/jcc examples/hello.c /tmp/hello.elf
# C source -> JetOS native ELF64

make mkjetfs && ./build/mkjetfs build/jetfs.img 128
make jetfs_import

./build/jetfs_import build/jetfs.img /tmp/hello.elf /hello.elf
# Insert the compiled ELF into JETFS

make esp && ./scripts/run_qemu.sh

# After booting, in jash:
run /hello.elf
```

`examples/hello.c` is a directly compilable and executable demonstration containing recursive Fibonacci and integer output.

`examples/prelude.c` is a reusable standard-library-style fragment containing `print_int`. Since JCC currently has no preprocessor, `#include` is not supported. Reusable code is therefore copied directly into the source file as a single translation unit.

## Verification Methodology

### 18. Build JCC itself with host GCC

`tools/jcc.c` is approximately 1,000 lines and contains the lexer, parser, type system, x86-64 encoder, and ELF64 writer in a single file.

It successfully compiles with **zero warnings on the first attempt**.

### 19. Verify the generated artifact using independent tools

The ELF generated by JCC was inspected using:

```bash
readelf -h -l
```

This confirmed that the output is a valid:

* ELF64 executable
* x86-64 executable
* `ET_EXEC`
* ELF containing valid `PT_LOAD` segments

The output was also disassembled using:

```bash
objdump -D
```

This was used to verify that instructions such as:

* `call`
* `mov`
* `test`
* `jz`

correctly target their intended addresses and that function-call fixups are correctly resolved.

The important point is that these checks were performed by **binutils' independent ELF/x86-64 tooling**, rather than by JCC itself.

### 20. Dynamic execution on a real CPU

A host harness (`run_harness.c`) was created because static verification alone was considered insufficient.

The harness:

1. Maps the generated program at its exact link address (`0x100000000`) using `mmap`.
2. Replaces the three syscall trampoline locations with host functions.
3. Uses the generated program's entry point as a real function pointer.
4. Executes the generated machine code directly on the host x86-64 CPU.
5. Uses `fork` to isolate individual test programs.

The following programs were actually executed:

* `return 42;` → actual process exit code `42`
* Recursive Fibonacci: `fib(10) = 55`
* Loops
* Array indexing
* String literals
* `_write`
* Short-circuit evaluation using `&&`
* Global variables
* Nested loops accumulating a value through `9`
* Character arrays
* Recursive `factorial(1..6)`
* Negative integer handling
* `print_int` from the prelude
* Pointer arithmetic scaling:

  * `int*` advances by 8 bytes
  * `char*` advances by 1 byte
* Pointer-based writes affecting the original array
* `&` / `*` combinations
* Operator precedence

The arithmetic expression:

```c
(2 + 3) * 4 - 10 / 2 % 3
```

was also evaluated correctly as:

```text
18
```

All relevant tests produced the expected results, including an **"ALL CHECKS PASSED"** result from the test suite.

### 21. Complete deployment pipeline

The complete deployment pipeline was executed:

```text
C source
   ↓
JCC
   ↓
ELF64
   ↓
mkjetfs
   ↓
JETFS image
   ↓
jetfs_import
   ↓
/hello.elf
```

All three host-side stages were actually executed successfully:

* `jcc`
* `mkjetfs`
* `jetfs_import`

The only missing step was booting the resulting image in QEMU because QEMU is not installed in the current sandbox.

However, the `run` command in jash was inspected and confirmed to read files through `jetfs_read`. Therefore, once the image is booted in an environment with QEMU, the generated ELF should follow the existing execution path.

See the known limitations section for the exact verification boundary.

# Milestone 30 — New Features

## JCC

JCC supports the following C subset:

* `int`
* `char`
* `void`
* Single-level pointers
* One-dimensional arrays
* Functions
* Up to 6 function arguments
* `if`
* `while`
* `for`
* `return`
* Arithmetic operators
* Comparison operators
* Logical operators
* Short-circuit evaluation

JCC converts this subset into actual x86-64 machine code.

The output is a static ELF64 executable intended to run as a Ring3 isolated process under JetOS.

---

## Minimal Runtime

JCC provides syscall trampolines for:

```c
_write(const char*)
_exit(int)
_gettick()
```

These wrap three of the four currently available JetOS system calls other than `SYS_BRK`.

User programs can call them as ordinary functions.

# Bugs / Issues Found During M30

This milestone was a new implementation, so there were no post-release bugs to fix. However, several real engineering problems were encountered during development.

### 24. Function and global-variable addresses are not known during initial code generation

When generating code, the final address of a function call target or global variable cannot always be known immediately.

The final size of the code and the location of the data section are not yet known.

The solution was a delayed fixup mechanism:

```text
Generate instruction
       ↓
Write placeholder address/value
       ↓
Record fixup location
       ↓
Finish code generation
       ↓
Resolve final addresses
       ↓
Patch placeholder
```

This is the same fundamental principle used by real assemblers and linkers for relocation handling, implemented here in a minimal form.

### 25. QEMU is unavailable in the test environment

Initially, static validation with `readelf` and `objdump` was considered.

However, static inspection alone was considered insufficient evidence that the generated machine code actually works.

A dynamic execution harness was therefore implemented.

The generated program is mapped at:

```text
0x100000000
```

and the three syscall trampoline locations are replaced with host functions.

The generated entry point is then called through a function pointer.

The trampoline slots were padded to 16 bytes, which also made this approach practical because a:

```text
movabs + jmp
```

sequence requires approximately 12 bytes.

Each test is isolated using `fork`, so even if generated code is invalid, the harness can safely recover the result.

# Known Limitations / Incomplete Work

All known M29 limitations remain valid, including:

* Partial text selection is not implemented.
* Dirty-rectangle rendering is not implemented.
* Other M29 limitations remain unchanged.

JCC-specific limitations are listed below.

| Item                               | Current Status                                                                                                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supported types                    | `int` / `char` / `void` / single-level pointers / one-dimensional arrays only. No structs, unions, enums, typedefs, `float`, or `double`.                                                                                                   |
| No preprocessor                    | `#include` / `#define` and similar preprocessing features are unavailable. Multiple source files and macros are therefore not supported. Reusable code must currently be copied into the same translation unit.                             |
| Function-wide scope                | Local declarations currently use flat function-wide scope rather than true C block scope. A variable declared inside a block remains visible until the end of the function.                                                                 |
| Missing syntax                     | No `switch`, `goto`, `do-while`, `++`, `--`, compound assignments such as `+=`, ternary operator, comma operator, or structs.                                                                                                               |
| No array initializer lists         | Syntax such as `int arr[3] = {1,2,3};` is not supported for local or global arrays. Elements must be assigned individually.                                                                                                                 |
| Global initialization restrictions | Only integer constants are supported for global initialization. String and pointer initializers are not supported. Local initialization such as `char *p = "text";` is supported.                                                           |
| Maximum 6 function arguments       | Only the System V register argument convention (`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`) is implemented. Stack-based arguments are not supported.                                                                                            |
| No real standard library           | There is no built-in `malloc`, `printf`, etc. `SYS_BRK` exists in the kernel, but JCC does not automatically provide `malloc`. Programs must implement their own `SYS_BRK` wrapper if needed.                                               |
| QEMU boot verification incomplete  | The mmap harness proves that generated machine code executes correctly on a real x86-64 CPU, but the complete JetOS Ring3 entry and syscall-dispatch path has not yet been verified through an actual QEMU boot in the current environment. |
| Other deferred work                | Alt+Tab, Recycle Bin, customizable desktop wallpaper, partial selection, and other previously deferred tasks were not addressed during M30. The milestone was dedicated to JCC.                                                             |

# Code Style / Design Principles

All M29 principles remain valid:

* Inspect the existing system before implementation.
* Reuse existing infrastructure whenever possible.
* Use host-side harnesses for isolated testing.
* Avoid unnecessarily large static buffers.
* Document deliberate simplifications.
* Define features honestly rather than relying on names.
* Prove that behavior remains unchanged after refactoring.

M30 adds two principles.

## 1. Decide external-tool dependencies based on project identity

Whether an external tool is acceptable should depend on whether it affects the project's core identity.

For example:

* RSA, SHA-256, and AES were implemented from scratch because avoiding external cryptographic dependencies is part of the project's identity.
* The JCC machine-code backend was implemented from scratch because direct code generation is part of the compiler's identity.
* The JCC executable itself is built using host GCC because this is merely development infrastructure, just like `mkjetfs.c`.

The distinction between:

```text
Core technology
```

and:

```text
Development infrastructure
```

should be considered explicitly for every new subsystem.

---

## 2. If static verification is insufficient, build a stronger dynamic verification method

The absence of QEMU should not automatically force the project to stop at static analysis.

M30 demonstrated this principle:

```text
No QEMU
   ↓
Static analysis is insufficient
   ↓
Design an alternative test
   ↓
mmap generated machine code
   ↓
Replace syscall trampolines
   ↓
Call generated entry point
   ↓
Execute directly on real x86-64 CPU
```

The preferred approach is therefore:

> **When the ideal verification tool is unavailable, design the strongest practical verification method using the tools that are available rather than settling for weaker evidence.**
